# 015. 큰 페이지 lint 가 플러그인을 죽였고, 죽은 뒤엔 아무도 복구할 수 없었다

> 관련 코드: `packages/figma-plugin/src/node-ops/tree.ts` (`TraversalBudget`, `tick`, `YIELD_EVERY`),
> `packages/server/src/websocket/server.ts` (`budgetMs` 계산), `packages/server/src/lint/run.ts` (`scanTimedOut`)
> 2026-08-08 실측 · 같은 날 수정

## 증상

한 파일에서 가장 큰 페이지(섹션 다수, y ~31000)에 `sigma_lint({scope:"page"})` 를 돌리면:

```
→ Figma Plugin 응답 시간 초과
```

**그 직후** 같은 pluginId 로는 어떤 호출도 안 됐다:

```
sigma_bind({pluginId:"figma-msk50ho0-uzik"}) → 플러그인이 연결되어 있지 않습니다
```

`sigma_list_plugins` 로 보면 **새 pluginId 로 재연결**돼 있다. 재현 **2/2**.

### 더 나빴던 것 — 재연결 루프

한 번 끊긴 뒤에는 약 **1분 간격으로 pluginId 가 계속 바뀌었다.**

```
08:54:20  figma-msk50ho0-uzik
08:56:27  figma-msk5388l-lp25
08:57:14  figma-msk5483i-fv1a
```

이 상태에서는 `sigma_get_node_info` 같은 **단일 노드 조회조차 타임아웃**했다. 직전 30분 동안
같은 pluginId 가 안정적이었으므로, 이 불안정은 **무거운 lint 이후 시작된 것**이다.

## 왜 심각한가

1. **호출자가 복구할 수 없다.** pluginId 가 계속 바뀌니 재시도하려면 매번 다시 받아야 하는데
   그 사이 또 바뀐다.
2. **부수 피해가 크다.** 이 저장소는 **여러 에이전트의 동시 작업을 공식 지원**한다
   (루트 CLAUDE.md 「멀티에이전트 동시 작업」). 한 에이전트의 lint 한 번이 **다른 에이전트들의
   세션까지 끊는다.**
3. **가장 필요한 곳에서 못 쓴다.** 큰 페이지일수록 lint 가 필요한데 바로 거기서 실패한다.

## 원인

`serializeTreeNode` 가 **완전 동기 재귀**였다. 노드가 많으면 그 재귀 하나가 Figma 플러그인
메인 스레드를 통째로 점유하고, 호스트가 하트비트를 처리하지 못해 Figma 가 플러그인을 재시작한다.

여기에 **예산 비대칭**이 겹쳤다. 서버는 `timeoutMs`(60초)로 스스로 포기하는데,
**플러그인은 그 값을 받은 적이 없다.** 서버가 포기한 뒤에도 플러그인은 계속 돌았고,
그 초과분이 정확히 Figma 가 플러그인을 죽이는 구간이었다.

## 무엇을 했나

**1. 순회를 양보한다.** `YIELD_EVERY`(2000) 노드마다 `await new Promise(r => setTimeout(r, 0))`.
매크로태스크로 넘겨야 호스트가 하트비트를 처리한다 — **이 한 줄이 "죽는다"와 "느리지만 끝난다"를 가른다.**
그러려고 `serializeTreeNode`/`attachChildren`/`getTreeWithFilter`/`findNodeWithDetails` 를 async 로 바꿨다.

**2. 죽는 대신 부분 결과를 준다.** `budgetMs` 를 넘기면 순회를 멈추고 거기까지의 결과에
`timedOut: true` 를 실어 돌려준다. `sigma_lint` 는 이것을 `scanTimedOut`/`scanWarning` 으로
노출하고 **`clean` 을 false 로 강제**한다(`scanTruncated` 와 같은 취급 — 원인은 달라도
"부분 스캔"이라는 성질이 같다).

**3. 예산을 서버가 정한다.** `budgetMs = WS 타임아웃 − 5초`.

## 되돌리면 안 되는 이유

- **플러그인 예산은 서버 타임아웃보다 반드시 짧아야 한다.** 같거나 길면 서버가 먼저 포기하고
  플러그인만 계속 도는 상태가 되는데, **그게 바로 이 사고의 조건**이다. 5초 여유는 응답
  직렬화·전송 몫이다.
- **`await` 를 "성능 손해"로 보고 걷어내지 말 것.** 동기 재귀가 빠른 건 맞지만, 빠르게 죽는다.
  이 순회는 완주가 성능이다.
- **`timedOut` 을 조용히 삼키지 말 것.** 부분 결과를 전체로 읽으면 "위반 0건"이 거짓이 된다 —
  이 저장소가 `scanTruncated`·`configUnreadable` 로 반복해서 막아 온 것과 같은 부류다.
- 양보 주기(2000)를 크게 올리면 양보 효과가 사라지고, 너무 낮추면 큰 페이지에서 순회가 느려진다.
  바꾸려면 실제 큰 페이지에서 재현 → 수정 후 완주 + 그 직후 `sigma_bind` 성공까지 확인할 것.

## 남은 것 (하지 않은 것)

- **`scope:"section"`** — 큰 페이지를 페이지 config·`annotation_layer` 면제를 유지한 채 나눠
  검사할 방법이 아직 없다(`nodeId` 스코프는 페이지 컨텍스트를 잃는다). 회피로가 하나 더 생기지만
  1+2 로 실질 해결돼 보류했다.
- **pluginId 회전 흡수** — 서버가 재연결을 같은 논리 세션으로 이어 주는 것. 근본 원인을 없앴으므로
  뒤로 미뤘다. 다시 필요해지면 그때는 오류 메시지에 *"`sigma_list_plugins` 로 id 를 다시 받으세요"*
  부터 넣는 것이 싸다.

## 후속 실측 (2026-08-09) — 죽지는 않지만 **완주도 못 한다**

같은 파일의 다른 큰 페이지(섹션 24개 · **25,011 노드**, 섹션별로 쪼개 세어 확인)에서
`sigma_lint({scope:"page"})` 가 **3회 연속 `Figma Plugin 응답 시간 초과`**.

- ✅ **위 수정은 살아 있다** — 플러그인이 **죽지 않았다**(pluginId 불변, 재연결 루프 없음).
  서버 1.59 / 플러그인 1.47 로 확인.
- ❌ **부분 결과 경로는 타지 않았다.** `treeTimeoutMs: 150000` · `treeNodeLimit: 60000` 으로 올려도
  **150초 뒤 에러**로 끝났다 — `scanTimedOut` 을 실은 부분 결과가 아니라 명령 자체의 실패다.
  즉 「2. 죽는 대신 부분 결과를 준다」가 **이 크기에서는 관측되지 않는다**(원인 미규명 — 순회가
  아니라 응답 직렬화/전송 구간에서 예산을 넘기는지 확인이 필요하다).
- 같은 시각 서버 로그에 **다른 드라이버가 같은 페이지에 `GET_TREE (depth: full)`** 를 돌리고 있었다.
  이 저장소는 동시 작업을 공식 지원하므로 **큰 페이지 + 동시 전수 조회**가 현실 조건이다.

### 「남은 것」의 전제 하나가 이미 바뀌었다

위 「남은 것」은 `scope:"section"` 이 필요한 이유로 *"`nodeId` 스코프는 페이지 컨텍스트를 잃는다"* 를
들었는데, **그 중 두 가지는 이미 고쳐져 있다**(2026-08-09 실측):

- 페이지 저장 config 가 유지된다 — `configSource: "merged"`, 커스텀 10종 전부 `coverage.customRan`.
- 기획 레이어 면제가 유지된다 — `collect-context.ts` 의 `scopeRoot?.type === 'SECTION'` 분기.
  같은 섹션을 page 스코프로 0건 확인한 뒤 `nodeId` 스코프로 재측정해도 0건이었고,
  대조군(범례에 확정 오타를 심어 `broken-hangul` 1건 발화 → 원문 복구 후 0)까지 통과했다.

⇒ 큰 페이지의 현실적 우회로는 **지금도 `nodeId` 스코프**이고, 남은 실질 결손은
`scopeContainerUnknown`(구버전 플러그인) 과 **섹션 간 관계 규칙**(`section_gap`·`section_overlap`)뿐이다.
`scope:"section"` 을 만들 때 이 실측을 출발점으로 쓸 것.
