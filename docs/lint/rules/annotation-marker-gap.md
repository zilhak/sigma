# `annotation_marker_gap`

| | |
|---|---|
| 기본 | **OFF** (opt-in) |
| 스코프 | [기획 레이어](../annotation-layer.md) 안 마커 |
| 추가 왕복 | **`get_tree`를 `includeAbsolute`로 호출** |
| 자동수정 | 없음 |

## 무엇을 잡나

마커가 가리키려는 대상을

- **덮고 있거나**
- 너무 **멀리 떠 있거나**
- 주변에 **가리킬 것이 아예 없는** 경우

## 왜 필요한가

규약은 "대상 경계에서 4~10px, 12px 초과 금지, 겹침 금지"인데 지금까지 기계 백스톱이 없었다.

실제 사례: 한 화면에서 **마커 14개가 전부 대상 위에 얹혀** 있던 적이 있고, 반대로 **그리지도 않은
위젯을 가리키는 마커**가 빈 공간에 찍혀 있던 적도 있다. 둘 다 검토에서 놓치기 쉽다 — 마커가 대상을
덮으면 오히려 "가리키고 있다"처럼 보이기 때문이다.

## 파라미터

| 이름 | 기본값 | 설명 |
|---|---|---|
| `maxGap` | **12px** | 대상 경계에서 이 거리를 넘으면 "떠 있음" |
| `orphanRadius` | **240px** | 이 반경 안에 대상 후보가 없으면 "가리킬 것 없음" |
| `markerAlias` | `marker` | 마커로 볼 스펙 alias |

## 비용 — 절대좌표가 필요하다

마커는 기획 레이어 안에 있고 대상은 상태 프레임 깊숙한 곳에 있어, **부모 로컬좌표로는 애초에 비교가
안 된다.** 그래서 이 규칙이 켜졌을 때만 서버가 `get_tree`를 `includeAbsolute`로 부른다 —
payload를 그때만 치른다.

## 오탐과 의도적 스코프 축소

- **대상 후보는 원자적 노드만**(자식 없는 leaf + INSTANCE). 상태 프레임 같은 큰 컨테이너를 후보에
  넣으면 마커는 언제나 그 위에 있게 되어 **전부 겹침**으로 판정된다.
- 덮음 판정은 실측으로 좁혔다 — 초기 구현은 바운딩박스가 조금만 스쳐도 덮었다고 봐서 오탐이 많았다.
- **영역을 가리키는 마커**처럼 일부러 멀리 두는 경우가 있다. 그건 면제로 처리한다.

## 면제하는 법

[`lint-ignore`](../suppress.md)로 노드별 면제 — reason에 "영역 지시" 같은 의도를 남긴다.

## 관련

번호 짝과 왕복 링크는 [`annotation_marker_pair`](annotation-marker-pair.md)가 맡는다.
