# 024. 쓰기를 섞어도 죽지 않았다 — 부하 재현으로 022 를 설명하려는 시도는 여기서 끝났다

> 이어지는 문서: [022](022-lifetime-log-never-fired-and-peak-was-invisible.md)(사망) ·
> [023](023-read-concurrency-did-not-reproduce-the-death.md)(읽기 동시성 기각)
> 재현 도구: `.claude-workspace/plugin-budget/` · 2026-08-13 실측 (서버 1.74)

## 왜 또 쟀나

023 이 읽기 동시성 가설을 기각하면서 남긴 유일한 후보가 **쓰기 경로**였다. 근거는 둘:

- 022 사망 인스턴스의 최다 명령이 **`MODIFY_NODE×571`**(GET_TREE 는 277)
- 치명 스택이 읽기가 아니라 쓰기였다 — `conditionalEditScope → cb → deepUnwrap ×14 → getPropStr`
  (**중첩 인자를 언랩하다** 죽었다)

023 의 프로브는 읽기만 던져 이 축을 통째로 안 건드렸다. 그래서 **Playground 파일**(사용자가
자유 실험용으로 열어 준 별도 파일)에 실험장을 만들고 022 의 명령 분포를 그대로 흉내냈다.

## 조건 — 022 를 모든 축에서 넘겼다

| | 022 (사망) | 이번 (생존) |
|---|---:|---:|
| 페이지 노드 수 | 12,925 | **13,355** |
| 지속 | 633초 | **903초** |
| 누적 수신 | 576.5MB | **1,187MB** (2.1배) |
| 유입 속도 | 0.91 MB/s | **1.31 MB/s** (1.45배) |
| 동시 (peak) | 6 | **6** (in-flight 을 계속 채움) |
| 명령 수 | 1,270 | 1,152 |

명령 분포도 022 의 가중치를 그대로 썼다:
`MODIFY 491 · TREE 252 · NODE_DATA 188 · NODES_INFO 107 · NODES_DATA 92 · PAGE_DATA 22`

쓰기는 **중첩 인자 위주**로 골랐다 — `setFills`(paint 배열 + color 객체),
`setEffects`(그림자 + color + offset 객체). `deepUnwrap` 가설을 정면으로 치기 위해서다.

## 결과 — **생존. 오류 0건. `Plugin disconnected` 0건.**

그리고 열화 곡선이 **022 와 정반대**였다. `recent rtt`(구간별 왕복, 022 에서 넣은 계측):

```
022 (사망): 10,545 → 15,676 → 21,095 → 34,090ms   ← 계속 오름
024 (생존):  5,095 →  5,658 →  4,908 →  3,451 → 5,422 → 4,035 → 5,820 → 6,479 → 4,575ms
                                                   ← 진동만, 추세 없음
```

022 당일에는 재조립 시간도 40ms 에서 14초로 튀었다. 여기서는 그런 신호가 **없다.**

## 그래서 무엇이 남았나

**부하 패턴으로 022 를 재현하려는 시도는 두 번 다 실패했다.**

| 가설 | 실측 | 결과 |
|---|---|---|
| 동시 전수 조회(읽기) | 023 — 동시 14 · 48.7MB in-flight · 누적 708MB | ⛔ 기각 |
| 읽기+쓰기 혼합 | 024 — 위 표 전부 초과 | ⛔ 기각 |

⇒ **«무엇을 얼마나 빨리 보냈나» 로는 설명되지 않는다.** 남은 것은 022 인스턴스가 **그때까지
누적해 온 상태**다. 022 는 **2시간 55분** 살아 있었고 그 전에 같은 페이지 전수 lint 를
10번 넘게 돌린 이력이 있었다([015](015-big-page-lint-killed-the-plugin.md) 두 번째 후속).
이번 실험 인스턴스는 20분짜리다. 파편화·잔존 힙처럼 **시간에 비례해 쌓이는 것**이 조건이라면
부하 실험으로는 원리적으로 못 잡는다.

### 다음에 시도한다면

- **장시간 방치 재현**: 낮은 부하로 2~3시간 유지한 뒤 그때 피크를 건다. 비싸지만 022 의
  «수명» 축을 유일하게 재현하는 방법이다.
- **VM 힙 직접 관측**(015·020·022 가 계속 미룬 것). `performance.memory` 로는 안 된다 —
  그건 UI iframe 의 힙이고 죽는 것은 렌더러 안의 wasm VM 이라 다른 메모리다.
- ⚠️ **재현될 때까지 큐·상한 같은 처방을 넣지 말 것.** 023 에서 한 번 근거 없는 처방을
  세울 뻔했다. 지금 있는 것은 «무엇이 원인이 아닌지» 둘뿐이다.

## 1.74 형제 연장의 프로덕션 검증 — 통과

Playground(트리 4.65MB/건)에서 동시 수를 1→18 로 올려 **60초 벽을 실제로 넘겼다**.

```
동시 15  OK×15  wall 53056ms
동시 16  OK×16  wall 55639ms
동시 17  OK×17  wall 58907ms
동시 18  OK×18  wall 61330ms   ← 원래 타임아웃(60초)을 넘겼는데 18개 전부 성공
```

그 순간 서버 로그에 구조 기록이 **15줄 동시에** 남았다:

```
Response still streaming: GET_TREE — 원래 타임아웃(60000ms)을 넘겼으나 응답이 오는 중이라
기다립니다 (60004ms 경과, 연장 20회, 상한 300000ms)      … ×15
```

**1.73(스트림별 연장)이었다면 이 중 첫 번째만 살고 나머지 14개는 여기서 죽었다.**
023 의 실측(N=4 에서 `{OK:1, TIMEOUT:3}`)이 정확히 그 모양이었다.

- 로그를 «경과 > 원래 타임아웃» 으로 좁힌 것도 여기서 값을 했다 — N=1~17 은 조용했고,
  실제로 구조가 일어난 N=18 에서만 15줄이 떴다. 첫 연장마다 찍었다면 매 라운드 수십 줄이
  묻혀 이 순간을 못 알아봤다.
- 연장 20~21회 / 상한 300초 대비 60초 사용 ⇒ 상한 계수 5 는 여유가 충분하다.

## 곁다리로 드러난 것 — 연장은 «오는 중»만 덮고 «만드는 중»은 못 덮는다

[023](023-read-concurrency-did-not-reproduce-the-death.md) 의 타임아웃 연장(1.73/1.74)을
실제 파일에서 재검증하려다 이걸 봤다:

```
10:09:56  Plugin connected (재빌드로 새 인스턴스, 현재 페이지는 L2-1)
10:11:34  GET_TREE (L1-2) 전송 → 60초 동안 청크 0개 → EMPTY
10:13:23  (한참 뒤) Reassembled 6.28MB
```

갓 붙은 플러그인이 **아직 로드되지 않은 페이지**를 처음 훑는 구간에서는 청크가 **하나도**
나오지 않는다. 연장은 청크를 증거로 삼으므로 **발동할 자리조차 없다.**

- 이건 1.74 의 회귀가 **아니다.** 연장이 덮는 범위 밖이다.
- 그 구간의 담당은 015 의 순회 예산인데, **페이지 로딩까지는 막지 못하는** 것으로 보인다
  (미확인 — 로딩이 예산 시계 안에 들어오는지 확인이 필요하다).
- 실험 설계 교훈: **갓 붙은 플러그인으로 측정하지 말 것.** 대상 페이지를 한 번 완주시켜
  워밍업한 뒤에 재야 한다. 이걸 몰라서 1.74 재검증 1회분을 버렸다.

## 실험장에 대해

Playground 파일 `Page 1` 에 `LoadTest-0`~`LoadTest-7` 프레임 8개(총 13,355 노드)를 만들었다.
`.claude-workspace/plugin-budget/build-playground.ts` 로 언제든 다시 만들 수 있고,
`mixed-load.ts` 가 022 분포로 부하를 건다. **둘 다 Playground 파일에만 바인딩하도록 되어 있다** —
쓰기가 섞이므로 대상 파일을 잘못 잡으면 남의 작업을 망친다.
