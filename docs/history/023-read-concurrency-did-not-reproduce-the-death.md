# 023. 동시 읽기로는 죽지 않았다 — 022 의 진단과 「큐」 처방이 근거를 잃었다

> 관련: [022](022-lifetime-log-never-fired-and-peak-was-invisible.md) 「남은 것」의 동시 예산 실측
> 재현 도구·원본 로그: `.claude-workspace/plugin-budget/`
> 2026-08-13 실측 (서버 1.69)

## 왜 쟀나

022 사망 직전 4.8초에 전수 트리 조회 5개가 겹쳐 `pending: 6` 이었고, 그걸 보고
**«동시 전수 조회 폭주가 실질 원인»** 으로 읽었다. 처방으로 «무거운 명령 동시 상한(큐)» 을
제안했고, 상한을 몇으로 잡을지의 근거가 `pending: 6` 하나뿐이라 실측하기로 했다.

## 결과 — **재현되지 않았다**

### 1차: `📄 L1-2 · CI/CD·GitOps` (전수 트리 **19.05MB**)

| 동시 | 결과 | 소요 |
|---:|---|---:|
| 1 | OK | 22s |
| 2 | OK | 35s |
| 3 | OK (**57MB 동시 in-flight**) | 55s |
| 4~6 | 시간 벽 (플러그인 **생존**) | 134s 뒤 부분결과 도착 |

### 2차: `📄 L2-2 · 클러스터`, `limit:8000` 으로 **건당 3.48MB 고정** (변수를 N 하나로)

```
N= 1  OK   3.5MB  12.5s      N= 8  OK  27.8MB  22.7s
N= 2  OK   7.0MB   5.9s      N= 9  OK  31.3MB  27.8s
N= 3  OK  10.4MB   8.7s      N=10  OK  34.8MB  30.0s
N= 4  OK  13.9MB  11.3s      N=11  OK  38.3MB  33.2s
N= 5  OK  17.4MB  14.6s      N=12  OK  41.7MB  39.4s
N= 6  OK  20.9MB  17.1s      N=13  OK  45.2MB  40.9s
N= 7  OK  24.3MB  20.4s      N=14  OK  48.7MB  42.7s
```

**전부 통과. 실험 전체에서 `Plugin disconnected` 0건.**

### 022 의 사망 조건을 모든 축에서 넘겼는데 안 죽었다

| 축 | 022 (사망) | 이번 (생존) |
|---|---:|---:|
| 동시 최고 | 6 | **14** |
| 동시 총량 | ~33MB | **48.7MB** (1차에선 57MB) |
| 누적 수신 | 576.5MB | **708.4MB** |
| 수명 | 633초 | **6,656초** |

### 스케일링이 선형이다 — 그 자체가 «메모리가 아니다» 의 증거다

N=2..14 에서 건당 약 **2.8초씩 일정하게** 증가한다. 메모리 압박이면 GC 스래싱으로
**초선형**으로 꺾여야 한다 — 022 사망 당일 재조립 시간이 40ms 에서 14초로 튀었던 것처럼.
여기서는 그냥 일감이 늘어난 만큼만 느려졌다.

## 그래서 무엇이 틀렸나

- **«동시 전수 조회 폭주가 원인» 은 지지되지 않는다.** 022 에 그렇게 적었지만 읽기 동시성만으로는
  재현되지 않는다. `pending: 6` 은 사망과 **상관**이 있었을 뿐 원인이라는 근거가 아니었다.
- **따라서 「무거운 읽기 명령 동시 상한(큐)」 은 이 사망을 막지 못한다.** 022 「남은 것」에
  적어 둔 그 계획을 **이 실측을 보지 않고 그대로 구현하지 말 것.** 상한을 14 아래로 잡았다면
  멀쩡한 워크로드를 느리게 만들면서 사망은 그대로 났을 것이다.
- **느린 것과 죽는 것은 다르다.** 평균 왕복이 21.8초까지 올라갔는데도 플러그인은 살아 있었다.
  `recent rtt` 상승을 사망 임박으로 읽으면 안 된다.

## 남은 유력 후보 — **쓰기 경로**

022 사망 인스턴스의 명령 분포는 **`MODIFY_NODE×571`** 이 최다였고(GET_TREE×277),
치명 스택도 읽기가 아니라 **쓰기**였다: `conditionalEditScope → cb → deepUnwrap ×14 → getPropStr`.
이번 프로브는 **읽기만** 던졌으므로 그 축을 통째로 안 건드렸다.

⇒ 다음 재현은 **읽기+쓰기 혼합**이어야 한다. 다만 그건 사용자 파일을 실제로 변형하므로,
실험 전용 페이지를 만들어 거기서만 돌린다.

## 덤으로 닫힌 것 — [015](015-big-page-lint-killed-the-plugin.md) 의 미해결 질문

015 두 번째 후속은 «부분 결과 경로는 타지 않았다 … 순회가 아니라 **응답 직렬화/전송 구간에서**
예산을 넘기는지 확인이 필요하다» 로 끝나 있었다. **후자다.**

1차 N=4 에서 서버 로그가 이렇게 남았다:

```
07:53:15경  N=4 발사
07:55:29    TREE_RESULT 18.77MB 조립시간 134,900ms   ← 134초 뒤 도착
            이어서 17.99 → 17.20 → 13.20 → 12.44 → 11.67MB (동시 개수가 늘수록 덜 진행)
```

- 트리 크기가 계단식으로 줄어드는 것 = **`timedOut` 부분 결과가 실제로 만들어지고 있다.**
- 그런데 순회 예산(55초)이 멈춘 뒤 **직렬화 + 청킹 + 전송에 80초가 더** 걸려 134초에 도착한다.
- 서버 타임아웃 60초가 그 전에 터지므로 **호출자는 «부분 결과» 가 아니라 아무것도 못 받는다.**

⇒ **예산이 순회에만 걸려 있고 전송에는 없다.** 015 의 `budgetMs = WS타임아웃 − 5초` 는
«순회가 끝나면 곧 응답» 을 전제하는데, 동시 실행에서는 전송이 순회보다 오래 걸린다.

### 고친 것 — 타임아웃이 재는 대상을 «총 경과» 에서 «침묵 시간» 으로 바꿨다

로그로 시각을 맞춰 보면 결정적이다:

```
07:52:16.464  GET_TREE ×4 전송
07:53:14.54   CHUNK_START 도착        ← 응답이 오기 시작
07:53:16.46   서버 타임아웃(60초) 발화  ← 그 1.9초 뒤에 죽였다
07:55:29.44   CHUNK_END (부분 결과 18.77MB 완성)
```

**응답이 오는 중이었는데 끊었다.** 그래서 `extendPendingWhileStreaming()` 을 넣었다 —
`RESPONSE_CHUNK_START`·`RESPONSE_CHUNK` 를 받을 때마다 그 명령의 타임아웃을 다시 건다.

- ⚠️ **«타임아웃을 늘리는 우회» 가 아니다.** 늘리는 게 아니라 **재는 대상을 바꾼 것**이다.
  청크가 멈추면 원래 타임아웃 그대로 발화한다(테스트로 고정).
  012 가 «타임아웃을 늘리는 것은 처방이 아니다» 라고 적은 것과 충돌하지 않는다 —
  012 의 상황은 **이미 죽은** 플러그인을 더 기다리는 것이었고, 여기는 **살아서 보내는 중**이다.
- **무한 연장은 막는다**: `STREAM_TIMEOUT_MAX_FACTOR = 5` (원래 타임아웃의 5배가 절대 상한).
  실측에서 필요했던 총 시간이 194초이므로 60초 명령이면 300초 상한으로 충분하다.
  상한에 걸려 실패하면 오류에 **연장 횟수와 좁히는 방법**(nodeId 스코프·limit·fields)을 싣는다.
- 첫 연장만 로그에 남긴다(청크마다 찍으면 묻힌다):
  `Response streaming from …: GET_TREE — 타임아웃 연장 시작 (58098ms 경과)`
- 오류 문구를 `${timeoutMs}ms` 에서 **실제 대기 시간**으로 바꿨다. 연장이 있으면 설정값과
  실제가 달라져 설정값을 그대로 보고하면 거짓이 된다.

**되돌리면 안 되는 이유**: 이걸 빼면 큰 페이지에서 015 가 만들어 준 «부분 결과» 를 호출자가
**영영 못 받는다**(플러그인은 멀쩡히 만들어서 보내는데 서버가 도중에 끊으므로).
`STREAM_TIMEOUT_MAX_FACTOR` 를 없애 무한 연장으로 바꾸는 것도 안 된다 — 진짜로 못 끝내는
요청이 영원히 매달린다.

## 이번에 검증된 것 (되돌리지 말 것)

- **[021](021-plugin-to-server-had-no-chunking.md) 청킹이 전제 조건이다.** 이 파일의 주요 페이지는
  전수 트리가 **19.05MB · 23.36MB** 로 둘 다 16MB 상한을 넘는다. 청킹이 없으면 **1개도 못 받는다** —
  이 실험 자체가 불가능했다.
- **[022](022-lifetime-log-never-fired-and-peak-was-invisible.md) 의 세 축 발화가 값을 했다.**
  궤적 로그가 **28 명령 / 136MB** 에서 처음 발화했다 — 명령 수 축만 있었으면 실험 내내 침묵했다.
  `recent rtt` 를 구간마다 초기화한 것도: 전부 타임아웃된 구간이 **`recent rtt: 0ms`** 로 남아
  «완료된 왕복이 하나도 없었다» 가 그대로 읽혔다(누적 평균이었으면 10.5초에 묻혔다).

## 재현 방법

```bash
bun .claude-workspace/plugin-budget/concurrency-probe.ts "<페이지 이름 일부>" <최대N> [노드limit]
```

- 응답 본문은 절대 출력하지 않는다(MB 급이라 호출자 컨텍스트를 덮는다) — 크기·시간·판정만 낸다.
- **판정은 사망/시간초과/정상을 구분해야 한다.** 1차 프로브는 `!text.includes('"error"')` 로 셌는데
  **빈 응답이 «에러 문자열이 없으니 OK»** 가 되어 N=4~6 실패를 성공으로 보고했다. 라운드마다
  `sigma_list_plugins` 로 `pluginId` 가 바뀌었는지 봐야 사망을 확실히 잡는다.
- **건당 크기를 `limit` 으로 고정**하고 N 만 변수로 둔다. 안 그러면 큰 페이지에서 시간 벽이
  메모리 벽을 가린다(1차가 그랬다).
