# 016 · `regex` 조건에 pattern 이 없으면 전건이 매칭됐다

## 증상

`sigma_find_node` 로 특정 문자열을 가진 TEXT 를 찾는데, **어떤 패턴을 줘도 같은 개수**가 나왔다.

```
있을 리 없는 문자열   matchCount=1047
.*                 matchCount=1047
흔한 말             matchCount=1047
```

응답에 `error` 도 `truncated` 도 없고 `enriched: true` 라 상세 조회까지 정상으로 돌았다.
결과만 보면 "그 문자열이 페이지에 1047번 있다" 로 읽힌다.

## 원인

호출이 이랬다.

```json
{ "op": "regex", "field": "characters", "value": "2026-08-01 14:23:10" }
```

`regex` 의 패턴 인자는 **`value` 가 아니라 `pattern`** 이다. 그런데

* `value` 는 `equals` 의 인자라 `CHECK_KEYS` 에 들어 있다 → 「모르는 키」 검사에 안 걸린다
* `evalCheck` 는 `new RegExp(check.pattern || '')` 로 평가한다 → `pattern` 이 없으면 **빈 정규식**
* 빈 정규식은 **어떤 문자열에나 맞는다** → 그 check 가 사라진 것과 같아진다

즉 오타 하나가 «조건 없음 = 전건 매칭» 으로 조용히 무너졌다. 같은 파일 `assertQueryShape` 의
주석이 이미 경고하던 실패 방식인데(`select:{nameContains:…}` 사고), **연산자별 인자는 검사하지
않고 있었다.**

`op` 자체와 「모르는 키」는 막고 있었으므로, 남은 구멍은 **아는 키를 아는 연산자에 잘못 붙인 경우**
하나였다.

## 무엇을 했나

`assertQueryShape` 에 **연산자별 필수 인자 검사**를 넣었다.

| op | 필수 |
|---|---|
| `regex` | `pattern` (빈 문자열도 거부) |
| `oneOf` | `values` |
| `equals` | `value` |
| `range` | `min` 이나 `max` 중 하나 |

`regex` 인데 `value` 가 실려 있으면 «패턴은 value 가 아니라 pattern 에 넣습니다» 를 예시와 함께
덧붙인다 — 이 사고의 정확한 모양이라 한 번에 고칠 수 있게 했다.

테스트는 거부 6건 + **대조군 2건**(제대로 준 `pattern` 은 그대로 걸러지는지)을 같이 뒀다.
거부만 테스트하면 과하게 막아 놓고도 통과한다.

## 되돌리면 안 되는 이유

* **이 실패는 0건이 아니라 전건 방향이다.** 검색이 0건을 주면 사람은 조건을 의심하지만,
  1047건을 주면 "많이 찾았다" 로 읽고 넘어간다. 조용한 통과가 특히 비싼 자리다.
* 이 도구의 대표 용법 중 하나가 **「스펙을 지우기 전에 인스턴스가 0인지 확인」** 이다.
  거기서 조건이 사라지면 개수가 부풀어 오답이 되고, 반대로 부푼 수를 믿고 삭제를 미루는 것도
  판단을 흐린다.
* `op` 검사·모르는 키 검사만으로는 **못 잡는다** — `value` 는 아는 키이고 `regex` 는 아는 연산자다.
  둘 다 통과하는 조합이라 인자 단위 검사가 아니면 걸리지 않는다.
* 빈 패턴을 「전부 허용」으로 두는 편의는 없다. 정말 전부를 원하면 그 check 를 빼면 된다.
