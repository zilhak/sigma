# 010. 생성 계열에만 배열 입력이 없어 표 하나에 호출이 수십 번 들었다

> 관련 코드: `packages/server/src/mcp/handlers/component-spec.ts` (`createSpecInstance`, `instances` 배열)
> 2026-08-07 실측 · 2026-08-08 수정

## 증상

수정(`sigma_batch_modify`)·삭제(`sigma_batch_delete`)·텍스트 채우기
(`sigma_set_multiple_text_contents`)에는 배치가 있는데 **생성에는 없었다.**
`sigma_create_component_spec_instance` 는 1 인스턴스 = 1 호출이다.

그런데 목업 조립에서 가장 자주 만드는 것이 **표**이고, 호출자는
*"표는 조립해서 만든다 — 제품 네임스페이스에 표 스펙을 만들지 않는다"* 를 정책으로 확정해
**모든 표가 셀 인스턴스의 조합**이다. 즉 이 비용은 앞으로도 계속 든다.

멤버 관리 섹션(4열 × 9행) 실측 — 클론과 `set_multiple_text_contents` 로 **이미 최적화한**
결과가 22회. 클론 없이 정직하게 만들면 **셀 36 + 프레임 10 = 46회**다. 그리고 이 표는
한 섹션에 6~12번 반복되고, 섹션은 페이지당 10개 규모다.

같은 작업에서 `batch_modify` 로 LNB 행 10개를 1회에 옮겼고 텍스트 21개를 2회에 채웠다.
**배치가 있는 축은 이미 싸고, 없는 축(생성)만 비쌌다** — 비대칭이 문제였다.

## 무엇을 했나

`sigma_create_component_spec_instance` 가 **`instances` 배열도 받게** 했다.
원소는 단일 호출과 **같은 인자**를 그대로 쓴다. 부분 실패를 허용하고 `results[]` 에
`index` 와 개별 결과를, 봉투에 `created`/`failed` 를 싣는다.

### 배치 전용 도구(`sigma_batch_create_*`)를 만들지 않은 이유

`docs/tool-conventions.md` §3 이 **"단일 처리 도구 + `batch_*` 도구를 쌍으로 만들지 않는다.
같은 도구가 스칼라와 배열을 모두 받게 한다"** 고 못박고 있고, §6 로드맵은 기존
`batch_modify`/`get_nodes_info`/`set_multiple_*`/`batch_delete` 를 **없앨 부채**로 올려놨다.

즉 "이미 batch 가 셋이나 있으니 하나 더" 는 **선례가 아니라 반례**다 —
없애기로 한 패턴을 하나 더 만드는 것이 된다. 그래서 규약이 정한 형태로 구현했다.

### 스칼라와 배열이 같은 코드를 타게 했다

`createSpecInstance` 하나로 뽑아 양쪽이 그것을 부른다. 갈라 두면 한쪽에만 검증이 붙어
**"배치로 만들면 다르게 동작한다"** 가 되는데, 그건 배치를 못 믿게 만드는 결함이다.
props 사전 검증·파일 스코프 대조·줄바꿈 높이 경고가 배열 경로에서도 그대로 돈다.

## 정직하게 말해 둘 것 — 줄어드는 것은 MCP 호출 수다

이 변경은 **플러그인 왕복 수를 줄이지 않는다.** 인스턴스마다 `USE_COMPONENT_SPEC` 이
한 번씩 나간다(로컬 WS 라 실측 수십 ms). 줄어드는 것은 **MCP 호출 수 = 에이전트 턴 수**이고,
실측상 그쪽이 지배적인 비용이다(46회 → 1회). 왕복까지 줄이려면 플러그인 쪽에 배치 명령을
새로 만들어야 하는데, 그건 별개의 작업이고 이 변경의 이득을 먼저 확인한 뒤에 판단할 일이다.

## 되돌리면 안 되는 이유

- **부분 실패를 허용한다.** 하나가 틀렸다고 나머지를 버리면 재실행 비용이 배치의 이득을 넘는다.
- **빈 배열·상호배타는 조용히 넘기지 않고 거부한다.** "인자를 줬는데 아무 일도 안 일어남" 은
  이 저장소가 반복해서 없애 온 실패 유형이다.
- 스키마의 `required` 에서 `alias` 를 뺐다 — 두면 배열 전용 호출이 스키마 단계에서 먼저 막힌다.
  상호배타 검증은 핸들러가 한다.
